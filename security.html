How the encryption works

Written plainly, including the parts that are not reassuring. If you are deciding whether to trust this with something that matters, read the last section first.

What is encrypted

Every document edit, every cursor position, every chat message and every display name is encrypted with AES-GCM 256 in your browser before it touches the network. The relay receives a 12-byte nonce followed by ciphertext it has no key for.

Where the key comes from

Your room code and password are stretched with PBKDF2-SHA256 at 200,000 iterations into two separate values, using two different salts:

key  = PBKDF2(code + ":" + password, salt = "textshare|CODE")
auth = PBKDF2(code + ":" + password, salt = "textshare-auth|CODE")

The key never leaves your browser. The auth token is sent to the relay to prove you know the password. Because the salts differ, handing over the auth token tells an attacker nothing useful about the key. The relay hashes it on arrival and stores only SHA-256(auth), so even a full dump of its storage contains nothing that can be replayed.

The salt strings still say textshare. Those are cryptographic constants rather than branding, and changing them would lock every existing room out of its own data.

What the relay can see

It genuinely cannot read your text. It can see:

  • that a room with a given code exists, and how many sockets are attached
  • the size and timing of each frame, so it knows roughly when someone is typing
  • the IP address of everyone connected, as any web server would

It keeps no request log tying those together, but traffic analysis is a real limitation of any relay design and it would be dishonest to claim otherwise.

Who can get in

If a room has a password, the relay refuses the connection before a socket is ever opened. Without the password a stranger with the room code cannot read the text, and cannot write into it either. Rooms without a password are open to anyone who has the six characters.

The room code is not a secret in any meaningful sense: it travels in links, chat apps and screen shares. The password is the real boundary.

How long anything lasts

A room is erased once everyone has left and the timer you chose runs out: 10 minutes, an hour, or a day. Deletion is not a flag, it removes the stored frames. Whoever created the room can also delete it immediately, which disconnects everyone and erases it on the spot.

A copy also lives in your own browser via IndexedDB, so you can keep working offline. "Delete offline copy" in settings removes it from this device.

Owner rights

Creating a room mints a random 256-bit token stored in your browser. Only that browser can lock, suspend or delete the room. The relay holds only a hash of it. Clear your browser storage and those rights are gone permanently, with no recovery, by design.

What this does not protect against

A weak password. The code is public and the ciphertext passes through a server. A short password can be attacked offline. Use something long.

Anyone you invite. Everybody in the room holds the same key. There is no per-person access, and no way to un-share what someone has already read.

A compromised browser or device. Encryption in the page cannot help if the machine itself is not trustworthy.

A hostile version of this site. The code is served to you at load time, so whoever controls the hosting could serve something that leaks your key. This is an inherent limit of browser-delivered cryptography.

Inline scripts are still permitted by the CSP. The ES module import map has to be inline on static hosting, and there is no server here to mint a nonce. Everything else is locked down: object-src 'none', base-uri 'none', frame-ancestors 'none', form-action 'none'.

No formal audit. This is one person's project using standard WebCrypto primitives. It has not been reviewed by anyone else.
