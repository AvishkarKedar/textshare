Security and threat model

Plain description of what is protected, what is not, and how. If something here is wrong, please open an issue.

The short version

Your text is encrypted in your browser with a key derived from the room code and password. The relay forwards sealed bytes and never receives the key. It can see how much traffic a room has and when, and nothing about what is in it.

How keys are made

  • Key material is room code + ":" + password. With no password, the room code alone is the secret, so anyone who has the code can read the room. That is the intended behaviour for a quick share.
  • Encryption key: PBKDF2-SHA256, 200,000 iterations, salt textshare|CODE, producing an AES-GCM 256 key. This never leaves your browser.
  • Auth token: PBKDF2-SHA256, 200,000 iterations, different salt textshare-auth|CODE. This is sent to the relay to prove you know the password. Because the salt differs, holding the auth token tells an attacker nothing usable about the encryption key.
  • The relay stores only SHA-256(auth token), so even a dump of its storage contains nothing replayable.
  • Every frame is sealed with AES-GCM under a fresh random 96-bit IV.

What the relay can and cannot see

ItemVisible to the relay
Your text, file names, chat messages, cursor positionsNo - AES-GCM ciphertext only
Your password or encryption keyNo - never transmitted
The room codeYes - it routes on it
Whether a room has a passwordYes - one boolean
Number of connections, message sizes, timingYes - unavoidable for a relay
Your IP addressYes, transiently, for rate limiting. Not logged.

Access control

Knowing the code is not enough to connect to a password-protected room. The relay checks the auth token during the HTTP handshake and returns 403 before any socket opens. An earlier version let anyone connect and merely fail to decrypt, which meant a stranger could still write garbage into the shared log. That is fixed.

Room codes are reserved exclusively at creation. Two people cannot land on the same code with different keys.

Whoever creates a room controls it

Creating a room mints a random 256-bit owner token, kept in your browser's local storage. Only that browser can make the room read-only, suspend it, or delete it. The relay holds only a hash of the token. Clear your browser storage and you lose owner rights permanently - there is no recovery, by design.

Data lifetime

  • A room is erased from the relay 10 minutes after the last person disconnects. Longer windows (1 hour, 24 hours) are opt-in at creation.
  • Deleting a room wipes it immediately and disconnects everyone.
  • Your browser keeps a local offline copy in IndexedDB. "Delete from this device" in settings removes it.

Abuse limits

Per room: 30 connections, 120 messages per second, 256 KB per frame, 5 MB of log. Per IP: 120 room lookups per minute. Exceeding these gets you throttled, not banned.

What this does not protect you from

  • A weak password. A 6-character code with no password is guessable in bulk by a determined attacker. Set a password for anything sensitive.
  • Anyone you gave the link to. There is no per-person identity. The link is the credential.
  • A compromised device, keylogger, or someone reading over your shoulder.
  • A malicious version of this site. All browser-based end-to-end encryption shares this: if the server that hands you the JavaScript is hostile, it can hand you JavaScript that leaks the key. The code is public and the build is served as static files, but you are trusting the host at load time. For a threat model where that matters, use an audited native client.
  • Traffic analysis. Sizes and timing are visible.
  • Impersonation of display names. Names are self-asserted and unverified.

Browser hardening

The site sends a Content Security Policy, frame-ancestors 'none', object-src 'none', no-referrer, and HSTS. The policy still allows inline scripts, because the ES module import map must be inline on static hosting and there is no server to issue a nonce. No third-party script is loaded other than the version-pinned modules from esm.sh. Names, colours, and chat text arriving from other clients are inserted as text nodes and validated, never as HTML.

Reporting something

Open an issue at github.com/AvishkarKedar/textshare. For anything you would rather not post publicly, mark the issue as a security report and I will follow up privately.
